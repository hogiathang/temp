# Architecture Plan: Internal URL Shortener

## 1. Requirements & Constraints (clarified)
| Item | Assumption |
|------|-----------|
| Users | ~50 internal, trusted |
| Scale | Low write volume; redirects modest (thousands/day at most) |
| Features | Create short code, redirect, count clicks |
| Constraints | Simple, cheap, low-maintenance |
| Implied | Internal auth (SSO/VPN), no public abuse surface |

**Open questions for stakeholder alignment:**
- Custom/vanity codes required, or auto-generated only?
- Retention: do links/clicks ever expire?
- Is click *analytics* (timestamps, referrer) needed, or just a counter?
- Auth source — existing SSO, or shared internal network only?

## 2. Recommended Architecture
A single small web service + one relational database.

```
[User] -> [Reverse proxy / SSO] -> [App service] -> [SQLite/Postgres]
   POST /links  -> store (code, url, clicks=0)
   GET  /{code} -> lookup, increment clicks, 302 redirect
```

- **App**: one stateless service (Flask/FastAPI/Express).
- **Code generation**: base62 of an auto-increment ID, or random 6–7 chars with uniqueness check.
- **Click counting**: `UPDATE ... SET clicks = clicks + 1`. For low volume this is fine synchronously; defer to async only if redirect latency matters.

## 3. Alternatives Compared
| Option | Pros | Cons | Fit |
|--------|------|------|-----|
| **SQLite + single service** | Zero infra, trivial backup (one file), cheapest | Single-node, limited concurrent writes | ✅ Best for 50 users |
| Postgres + service | Concurrency, room to grow | Needs a managed DB / more ops | Good if growth expected |
| Serverless (Lambda + DynamoDB) | Scales to zero, no servers | More moving parts, vendor lock-in, cold starts | Overkill here |
| Off-the-shelf (e.g. self-hosted Shlink/YOURLS) | No build, batteries included | Less control, another app to patch | Worth it if "buy > build" |

**Recommendation:** Build-minimal on SQLite first; the "buy" option (YOURLS/Shlink) is a strong shortcut if no custom logic is needed.

## 4. Risks & Dependencies
- **Single point of failure** (one node/file) — acceptable internally; mitigate with daily DB backup.
- **Code collisions** — handle with unique constraint + retry.
- **Open redirect risk** — even internal: validate scheme (`http/https` only).
- **Click-count race conditions** — atomic SQL increment avoids this.
- **Dependency**: auth integration (SSO) is the main external dependency.

## 5. Phased Rollout
1. **MVP** — create + redirect + counter on SQLite, behind existing network auth. (~1–2 days)
2. **Hardening** — input validation, unique-constraint retry, automated backups, basic logging.
3. **Usability** — small web UI, list/search own links.
4. **Scale-if-needed** — migrate SQLite→Postgres, add async click logging only if metrics show pressure.

**Decisions needing alignment:** build-vs-buy, auth source, and whether per-click analytics are in scope.
